## Why

Order links are generated by hand. The manager picks a client in the back office,
generates a link, and pastes it into the WhatsApp conversation the customer
started. We are introducing an automated agent that does this on the customer's
message instead, and the API cannot serve it as it stands.

**An inbound message carries a phone number, not a client.** The directory holds
one — it was given an optional, unique, normalized phone precisely so an inbound
message could be resolved against it — but nothing exposes that resolution. The
only route to a client id is to retrieve the whole directory and search it, on
every message, with no answer to the question the agent asks first: is this
number a customer at all, or a stranger whose message should be dropped?

**Generating a link is not repeatable.** Every request mints a new token and a
new order, so a customer who writes twice produces two live links and two orders.
The bloque lists every order it holds regardless of whether it was ever filled
in, so each surplus link becomes an empty row the manager cannot account for and
will never see resolved. The manual flow has this too — generating twice for the
same client leaves a row behind permanently — but it takes a deliberate double
click, where an agent answering messages leaks one per message.

The two are one change because they are one conversation: resolve the sender,
drop them if they are unknown, otherwise hand back their link for the open
bloque — the one they already have if they have one.

## What Changes

- **A client can be resolved by phone number.** One request, matching on the
  normalized digits so it resolves however the number was typed, answering with
  the client or with a plain "no such client" — the latter a normal answer, not
  an error, because distinguishing a customer from a stranger is the ordinary
  first question and its negative case is not a failure.
- **Generating a link for a client who already has one returns that link.**
  Scoped to the open bloque and to links not yet used, which are exactly the
  conditions under which a link is still good. A consumed link is never handed
  out again, and closing a bloque starts everyone fresh.
- **Orders record how they came to exist** — from a generated link, or
  transcribed by hand in the back office. Only the first may be given to a
  customer.
- **The back office is unchanged.** **Generar link** behaves as before from the
  manager's side, minus the empty orders a repeated click used to leave behind.
  It gains no indication that a link it shows was already outstanding; the
  manager generating a link twice for the same client now simply gets the same
  one.

## Capabilities

### Modified Capabilities
- `client-directory`: a client can be resolved by phone number.
- `order-links`: link generation returns a client's existing link for the bloque
  rather than issuing a second, and orders record their origin.

## Impact

**Schema:** `Order` gains a `source` column recording origin, added by `ALTER
TABLE` with a default rather than a table rebuild. It defaults to `manual`, which
is the safe reading of history: existing rows are a mix of both origins and
nothing can recover which is which, so treating them all as manual means no
historical row is ever handed out. The opposite default would offer every past
manually-transcribed order to a customer.

**Backend:** the directory gains a by-phone resolution; link generation looks for
a live link before creating one; manual order creation stamps its origin.

**Frontend:** none.

**The origin column is load-bearing, not bookkeeping.** A manually transcribed
order carries an unused token and an unset consumption marker, exactly like a
freshly generated link, so without recording origin the two are indistinguishable
— and confirming an order *appends* its items rather than replacing them, so
handing a manual order to a customer would stack their items on the manager's and
double that product's production totals. This is why reuse keys on origin rather
than on an order merely looking empty.

**Phone normalization stays digits-only,** the provisional decision recorded when
the directory was given a phone. This change resolves against whatever is stored
and does not settle whether numbers must carry a country code — the agent matches
what the manager typed, so a directory holding local-format numbers will not
resolve an inbound international one. That remains open, and is now a
backfilling question rather than a schema one.

**Reuse is enforced in application code only.** Two genuinely simultaneous
requests for the same client could still both create a link, since nothing in the
database forbids it. A single agent handling messages in sequence does not
produce that race; a partial unique index is the fix if it ever does.

**The endpoints are unauthenticated,** like every other back-office endpoint on
the backend, which is reachable only from the private network. Exposing the
backend publicly would now also expose resolving the directory by phone number.
